    문제

    해결 방안 검토
    사용자와 관리자의 권한이 다르더라도, 같은 토큰 생성·검증 로직까지 따로 관리하면 동일한 정책을 반복해서 수정해야 합니다. 다만 중복을 줄이는 과정에서 권한 구분까지 없어져서는 안 됩니다. 따라서 권한 정보는 구분하고, 동일하게 동작해야 하는 토큰 처리만 공통화하기로 했습니다.

    회원 코드에서 보관함 처리를 직접 호출하면 보관함의 변경이 회원 기능에 영향을 줍니다. 그렇다고 두 처리를 독립적으로 완료시키면 회원 처리만 성공하고 필요한 보관함 처리는 실패한 상태가 생길 수 있습니다. 따라서 호출 관계는 이벤트로 분리하되, 두 작업의 성공과 실패는 같은 트랜잭션으로 묶는 방식을 선택했습니다.
    해결·개선
    토큰 생성과 검증을 공통화해 공통 인증 정책의 수정 지점을 모았습니다. 가입·탈퇴에 따른 보관함 처리는 이벤트 핸들러로 분리하고, 이벤트 처리는 기존 트랜잭션에 참여하도록 구성했습니다.
    성과

    동시 저장 요청의 중복과 보관함 용량 초과 제어

    문제
    여러 사용자가 같은 보관함에 동시에 저장하면, 각 요청이 모두 ‘아직 저장되지 않은 카드’ 또는 ‘50장 미만’이라고 판단할 수 있었습니다. 이 상태로 저장하면 같은 카드가 중복되거나 50장 제한을 넘을 위험이 있었습니다.
    해결 방안 검토
    카드별로 잠그면 서로 다른 카드의 동시 저장은 제어할 수 없어 보관함 단위의 잠금이 필요했습니다. 앞선 저장이 DB에 확정된 뒤 다음 요청이 카드 수와 중복 여부를 확인하도록, 트랜잭션 종료까지 잠금을 유지하기로 했습니다.
    해결·개선
    보관함 ID를 기준으로 Redisson 분산 락을 적용하고, 잠금을 획득한 요청만 별도 트랜잭션에서 저장 조건을 확인하도록 했습니다. 이미 있는 카드는 추가하지 않고, 50장에 도달한 보관함에는 새 카드 저장을 거절했습니다. DB 커밋 또는 롤백 후 잠금을 해제하도록 구성했습니다.
    성과
    보관함 단위로 저장을 제어해, 동시 요청에 따른 카드 중복과 용량 초과 위험을 줄였습니다.

    강의 승인을 기다리게 하지 않는 AI 요약 작업 처리

    문제
    강의 승인과 AI 요약을 연결할 때, 관리자가 분석 완료까지 기다리는 상황과 승인된 강의의 분석 작업이 누락되는 상황을 피해야 했습니다.
    해결 방안 검토
    승인 요청 안에서 분석하면 관리자가 기다려야 하고, 승인 이후 별도로 호출하면 호출 실패 시 작업이 누락될 수 있었습니다. 승인 대기와 작업 누락 위험을 함께 줄이기 위해, 승인 정보와 작업 기록은 같은 트랜잭션으로 저장하고 실제 분석은 분리하는 Outbox 방식을 선택했습니다.
    해결·개선
    강의 승인과 영상별 분석 작업 등록을 하나의 트랜잭션으로 묶고, 분석 서버가 작업을 가져가 결과를 전달하는 API를 구현했습니다. 작업은 대기, 처리 중, 완료, 실패 상태로 관리하고 중복 등록을 제한했습니다.

    분석 서버가 실패를 알린 작업은 1분, 5분, 60분 뒤에 다시 가져갈 수 있도록 최대 3회의 재시도 기준을 마련했습니다.
    성과
    AI 분석 완료를 기다리지 않고 승인하며, 승인만 완료되고 분석 작업은 등록되지 않는 위험을 줄였습니다.

    리뷰마다 반복하던 작성자 정보 조회 개선

    문제
    리뷰 목록에 닉네임을 표시하려고 리뷰마다 회원 정보를 따로 조회했습니다. 같은 작성자의 정보도 반복해서 가져와, 리뷰가 늘어날수록 DB 조회가 함께 늘어나는 구조였습니다.
    해결 방안 검토
    줄여야 할 것은 리뷰 조회 자체가 아니라, 각 리뷰에 닉네임을 붙이면서 반복되는 회원 조회였습니다. 현재 페이지의 리뷰에서 필요한 작성자 ID를 모두 알 수 있으므로, 리뷰마다 회원을 조회하는 대신 작성자 ID를 모아 한꺼번에 조회하는 방식을 선택했습니다. 기존 페이지 처리를 바꾸지 않고도 같은 작성자의 정보를 여러 리뷰에서 재사용할 수 있기 때문입니다.
    해결·개선
    현재 페이지의 리뷰에서 작성자 ID를 모아 중복을 제거한 뒤 회원 정보를 일괄 조회했습니다. 조회 결과를 ID별 닉네임으로 연결해 각 리뷰의 응답을 구성했습니다.
    성과
    작성자 정보를 재사용해, 리뷰마다 반복되던 작성자 DB 조회를 줄였습니다.

    긴 AI 처리 중에도 접수 여부와 진행 단계를 확인할 수 있도록, 접수 응답과 실행을 분리하기로 했습니다. 후속 생성 단계의 예외로 전체를 실패 처리하면 이미 확보한 원문도 제공하지 못하므로, 해당 단계만 원문이나 기본 문구로 대체해 기록을 남기는 방식을 선택했습니다.
    해결·개선
    음성과 일기 정보를 저장한 뒤 HTTP 202 응답과 일기 ID를 먼저 반환하고, BackgroundTasks로 AI 처리를 이어갔습니다. 단계가 바뀔 때마다 진행 안내를 DB에 기록했습니다.

    일기 본문 생성 중 예외가 발생하면 인식한 원문을 사용하고, 제목과 위로 문구는 각각 본문 첫 줄과 기본 문구로 대체했습니다.
    성과
    사용자가 현재 처리 단계를 확인하고, 일부 생성 단계에 실패해도 확보한 내용을 결과로 받을 수 있게 했습니다.

    해결 방안 검토
    인식 모델과 입력 음성 양쪽을 개선 대상으로 잡았습니다. 파일 형식을 맞춰도 음량 차이는 남기 때문에, 모델 설정 변경과 함께 음량 정규화를 추가하기로 했습니다.

    성과

    대표 감정 하나만 집계하던 통계 개선

    문제
    한 일기에 기쁨과 슬픔이 함께 분석돼도 통계에는 대표 감정 하나만 집계됐습니다. 저장된 다른 감정 점수가 빠져, 사용자는 분석된 감정 분포를 통계에서 확인할 수 없었습니다.
    해결 방안 검토
    대표 감정별 일기 수를 세면 한 일기에서 함께 분석된 다른 감정은 통계에 반영되지 않습니다. 대표 감정뿐 아니라 함께 분석된 감정도 보여주기 위해 감정별 점수를 합산하는 방식을 선택하고, 리포트와 운영 대시보드의 집계 기준을 맞췄습니다.
    해결·개선
    처리가 완료된 일기의 감정별 점수를 합산하고, 집계 값이 없는 감정은 0으로 표시했습니다. 리포트 API와 운영 대시보드를 동일한 점수 누적 방식으로 맞췄습니다.
    성과
    대표 감정에 가려졌던 나머지 감정 점수까지 통계에 반영해, 분석된 감정 분포를 확인할 수 있게 했습니다.
