    문제
    회원 코드가 가입·탈퇴에 필요한 보관함 처리를 직접 호출해, 보관함 처리 방식이 바뀌면 회원 코드도 함께 검토해야 했습니다.
    해결 방안 검토
    회원 코드에서 보관함 처리를 직접 호출하면 보관함의 변경이 회원 기능에 영향을 줍니다. 그렇다고 두 처리를 독립적으로 완료시키면 회원 처리만 성공하고 필요한 보관함 처리는 실패한 상태가 생길 수 있습니다. 따라서 호출 관계는 이벤트로 분리하되, 두 작업의 성공과 실패는 같은 트랜잭션으로 묶는 방식을 선택했습니다.
    해결·개선
    가입·탈퇴에 따른 보관함 처리는 이벤트 핸들러로 분리하고, 이벤트 처리는 기존 트랜잭션에 참여하도록 구성했습니다.
    성과
    회원 서비스의 보관함 직접 호출을 2곳에서 0곳으로 줄여, 보관함 처리 변경을 회원 코드와 분리하고 기능별 유지보수성을 높였습니다.

    동시 저장 요청의 중복과 보관함 용량 초과 제어

    문제
    여러 사용자가 같은 보관함에 동시에 저장하면, 각 요청이 모두 ‘아직 저장되지 않은 카드’ 또는 ‘50장 미만’이라고 판단할 수 있었습니다. 이 상태로 저장하면 같은 카드가 중복되거나 50장 제한을 넘을 위험이 있었습니다.
    해결 방안 검토
    카드별로 잠그면 서로 다른 카드의 동시 저장은 제어할 수 없어 보관함 단위의 잠금이 필요했습니다. 앞선 저장이 DB에 확정된 뒤 다음 요청이 카드 수와 중복 여부를 확인하도록, 트랜잭션 종료까지 잠금을 유지하기로 했습니다.
    해결·개선
    보관함 ID를 기준으로 Redisson 분산 락을 적용하고, 잠금을 획득한 요청만 별도 트랜잭션에서 저장 조건을 확인하도록 했습니다. 이미 있는 카드는 추가하지 않고, 50장에 도달한 보관함에는 새 카드 저장을 거절했습니다. DB 커밋 또는 롤백 후 잠금을 해제하도록 구성했습니다.
    성과
    동시 요청에 따른 중복 저장과 용량 초과를 제어해, 공동 보관함 데이터의 정합성을 높였습니다.
    검증: 로컬에서 두 시나리오를 각각 30회 비교했습니다. 잠금만 생략한 대조군에서는 같은 카드의 중복 저장과 서로 다른 카드의 50장 초과가 각각 30회 발생했고, 잠금 적용 시에는 둘 다 0회였습니다.

    보관함 미리보기에 필요한 카드만 조회하도록 개선

    문제
    보관함 목록에는 최신 카드 3장만 표시하지만, 전체 카드를 가져온 뒤 애플리케이션에서 정렬하고 3장을 골랐습니다. 저장된 카드가 많아질수록 화면에 쓰지 않는 데이터까지 가져와 처리해야 했습니다.
    해결 방안 검토
    서버의 정렬 방식을 개선하더라도 전체 카드 데이터를 가져오는 부담은 남습니다. 보관함마다 최신 3장만 필요하므로 DB에서 보관함별로 선별하는 방식을 선택했습니다. 전체 카드 수도 표시해야 하므로 기존 집계는 유지했습니다.
    해결·개선
    ROW_NUMBER 윈도 함수로 보관함별 최신 카드 3장만 조회하도록 변경했습니다. 서버의 전체 카드 정렬 코드를 제거하고, 선별된 카드를 보관함별로 묶어 기존 카드 수 집계 결과와 함께 응답하도록 했습니다.
    성과
    미리보기 정보를 유지하면서 DB에서 가져오는 카드 연결 데이터를 1,000행에서 60행으로 94% 줄여, 목록 조회에 필요한 데이터 처리 부담을 낮췄습니다.
    측정 조건: 로컬 합성 데이터로 사용자 100명의 보관함 목록을 비교했습니다. 사용자별 보관함 20개 × 카드 50장으로 구성했고, 변경 전후 스키마와 인덱스는 동일합니다.

    강의 승인을 기다리게 하지 않는 AI 요약 작업 처리

    문제
    강의 승인과 AI 요약을 연결할 때, 관리자가 분석 완료까지 기다리는 상황과 승인된 강의의 분석 작업이 누락되는 상황을 피해야 했습니다.
    해결 방안 검토
    승인 요청 안에서 분석하면 관리자가 기다려야 하고, 승인 이후 별도로 호출하면 호출 실패 시 작업이 누락될 수 있었습니다. 승인 대기와 작업 누락 위험을 함께 줄이기 위해, 승인 정보와 작업 기록은 같은 트랜잭션으로 저장하고 실제 분석은 분리하는 Outbox 방식을 선택했습니다.
    해결·개선
    강의 승인과 영상별 분석 작업 등록을 하나의 트랜잭션으로 묶고, 분석 서버가 작업을 가져가 결과를 전달하는 API를 구현했습니다. 작업은 대기, 처리 중, 완료, 실패 상태로 관리하고 중복 등록을 제한했습니다.

    분석 서버가 실패를 알린 작업은 1분, 5분, 60분 뒤에 다시 가져갈 수 있도록 최대 3회의 재시도 기준을 마련했습니다. 처리 중 상태에서 10분 넘게 갱신되지 않은 작업도 주기적으로 확인해, 같은 재시도 한도 내에서는 대기 상태로 되돌리고 한도를 넘으면 실패로 종료했습니다.
    성과
    AI 분석과 승인을 분리해 관리자의 승인 대기 부담을 줄이고, 승인과 분석 작업을 함께 저장해 작업 연결의 안정성을 높였습니다.
    검증: 로컬 테스트 워커로 작업 100건 중 일시 실패 30건과 응답 중단 10건을 주입해 3회 검증한 결과, 매회 100건 모두 완료되고 누락은 0건이었습니다.

    리뷰 목록을 구성하면서 작성자와 수강 정보를 리뷰마다 조회해, 리뷰 수가 늘어날수록 DB 조회도 늘어났습니다. 작성자를 일괄 조회한 뒤에도 작성자 ID를 읽는 과정에서 수강 정보의 지연 로딩이 발생했습니다.
    해결 방안 검토
    작성자 정보는 현재 페이지에서 ID를 모아 일괄 조회하고, 리뷰와 단일 연관관계인 수강 정보는 리뷰 조회 시 함께 가져오기로 했습니다. 응답에 필요한 관계만 조회하면서 기존 페이징과 응답 형식을 유지할 수 있기 때문입니다.
    해결·개선
    작성자 ID의 중복을 제거해 회원 정보를 일괄 조회하고, EntityGraph로 수강 정보를 함께 조회하도록 개선했습니다. 응답 내용과 총건수를 비교하고, 정렬과 페이지 경계 및 숨김 리뷰 제외 동작을 검증했습니다.
    성과
    리뷰 10개 조회의 SQL 실행을 24회에서 5회로 약 79% 줄여, 리뷰 목록을 구성할 때 발생하는 DB의 반복 조회 부담을 낮췄습니다.
    측정 조건: 로컬 합성 리뷰 1만 개, 작성자가 서로 다른 리뷰 10개 기준. 작성자 일괄 조회 적용 후 15회, 수강 정보 조회 개선 후 5회로 확인했습니다. 수강 정보 개선은 개인 후속 검증 결과입니다.

    배포 스크립트의 중복 실행 제거와 백업 관리

    문제
    배포 스크립트가 같은 애플리케이션의 실행을 중복으로 시도했습니다. 백업 파일에도 보관 기준이 없어 배포를 반복할수록 오래된 파일이 쌓였습니다.
    해결 방안 검토
    실행 명령을 하나로 줄이더라도 필요한 환경 설정은 빠짐없이 전달돼야 했습니다. 따라서 설정을 전달하는 명령을 기준으로 통합하기로 했습니다. 백업은 모두 보관하면 계속 쌓이고, 모두 삭제하면 이전 버전으로 복구할 수 없습니다. 그래서 복구에 사용할 최근 버전은 남기면서 보관 개수를 제한하는 기준을 선택했습니다.
    해결·개선
    중복된 실행 명령을 제거하고 필요한 설정을 전달하는 명령 하나로 통합했습니다. 백업은 최신 3개만 남기도록 오래된 파일을 정리하는 절차를 추가했습니다.
    성과
    중복 실행을 제거하고 백업을 최신 3개로 관리해, 배포 절차를 단순화하고 백업 파일 관리 부담을 줄였습니다.

    AI 처리 단계 안내와 생성 실패 시 대체 결과 제공

    문제
    음성 인식부터 일기 생성까지 여러 단계를 거치는데, ‘처리 중’만 표시하면 사용자는 어디까지 진행됐는지 알 수 없었습니다. 본문이나 위로 문구 생성에 실패했을 때, 이미 인식한 원문까지 결과로 제공하지 못하는 상황도 피해야 했습니다.
    해결 방안 검토
    긴 AI 처리 중에도 접수 여부와 진행 단계를 확인할 수 있도록, 접수 응답과 실행을 분리하기로 했습니다. 후속 생성 단계의 예외로 전체를 실패 처리하면 이미 확보한 원문도 제공하지 못하므로, 해당 단계만 원문이나 기본 문구로 대체해 기록을 남기는 방식을 선택했습니다.
    해결·개선
    음성과 일기 정보를 저장한 뒤 HTTP 202 응답과 일기 ID를 먼저 반환하고, BackgroundTasks로 AI 처리를 이어갔습니다. 단계가 바뀔 때마다 진행 안내를 DB에 기록했습니다.

    일기 본문 생성 중 예외가 발생하면 인식한 원문을 사용하고, 제목과 위로 문구는 각각 본문 첫 줄과 기본 문구로 대체했습니다.
    성과
    처리 단계 안내로 사용자의 진행 상황 파악을 돕고, 본문 생성 실패 시에도 인식한 원문을 제공해 기록을 다시 작성해야 하는 부담을 줄였습니다.

    해결 방안 검토
    인식 모델과 입력 음성 양쪽을 개선 대상으로 잡았습니다. 파일 형식을 맞춰도 음량 차이는 남기 때문에, 모델 설정 변경과 함께 음량 정규화를 추가하기로 했습니다.

    성과

    대표 감정 하나만 집계하던 통계 개선

    문제
    한 일기에 기쁨과 슬픔이 함께 분석돼도 통계에는 대표 감정 하나만 집계됐습니다. 저장된 다른 감정 점수가 빠져, 사용자는 분석된 감정 분포를 통계에서 확인할 수 없었습니다.
    해결 방안 검토
    대표 감정별 일기 수를 세면 한 일기에서 함께 분석된 다른 감정은 통계에 반영되지 않습니다. 대표 감정뿐 아니라 함께 분석된 감정도 보여주기 위해 감정별 점수를 합산하는 방식을 선택하고, 리포트와 운영 대시보드의 집계 기준을 맞췄습니다.
    해결·개선
    처리가 완료된 일기의 감정별 점수를 합산하고, 집계 값이 없는 감정은 0으로 표시했습니다. 리포트 API와 운영 대시보드를 동일한 점수 누적 방식으로 맞췄습니다.
    성과
    대표 감정 외의 점수도 집계해, 사용자가 기록에 함께 나타난 여러 감정의 분포를 파악하도록 개선했습니다.
